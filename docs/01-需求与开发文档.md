# 漏洞管理平台 — 需求与开发文档

> 版本：v0.1（草案，待评审冻结）
> 更新日期：2025-01-01
> 关联文档：[`02-API接口文档.md`](./02-API接口文档.md)、[`openapi.yaml`](./openapi.yaml)

---

## 1. 项目背景

公司/团队在各源代码管理仓库（GitHub / GitLab / Gitee 等）中推送代码时，需要自动做安全扫描，并把结果集中管理起来。

现状与流程（根据需求方口述整理）：

1. 扫描工具由**扫描侧**（下称"国庆团队"）开发，以能力的形式挂载到 GitHub / GitLab 等代码仓库上。
2. 项目提交代码（push / MR）时，CI 会把扫描工具拉下来并执行。
3. 扫描工具扫描完成后，会产生两类数据：
   - **漏洞信息**：发现的漏洞明细（含文件、行号、代码片段、规则、等级）。
   - **正负样本**：所有扫描过的文件样本 —— 有漏洞的为**正样本**，无漏洞的为**负样本**。
4. 扫描工具通过 HTTP 调用**漏洞管理平台的 API**，把上述数据上报。
5. 平台入库（MySQL）。
6. 使用者通过**登录界面**登录平台，查看漏洞数据、做统计与处置。

**核心诉求：先冻结 API 接口契约，再并行开发。**
需求方明确强调：必须先与扫描侧把 API 定下来，否则两边都会卡住。因此本文档的第 6 章与 [`02-API接口文档.md`](./02-API接口文档.md) 是本阶段的**第一优先级交付物**。

## 2. 项目目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 打通"扫描 → 上报 → 入库"链路 | 扫描工具一次调用即可完成数据上报，幂等、可重试 |
| G2 | 数据可视化 | 登录后能看到漏洞列表、详情、统计看板 |
| G3 | 样本沉淀 | 正负样本入库，后续可用于扫描引擎的模型/规则调优 |
| G4 | 契约先行 | API 文档 + OpenAPI 文件 + Mock Server，双方可并行开发 |
| G5 | 工程可交付 | Node.js + React + Ant Design + MySQL，可本地一键起、可部署 |

## 4. 名词约定

| 名词 | 含义 |
|---|---|
| 扫描侧 / 上报方 | 扫描工具（CI 中执行），调用平台 API 的一方 |
| 平台侧 | 本漏洞管理平台（后端 + 前端） |
| 正样本（positive） | 被扫描的文件中**包含漏洞**的样本 |
| 负样本（negative） | 被扫描的文件中**不包含漏洞**的样本 |
| 扫描批次 / Scan | 一次扫描任务的完整结果集，上报的最小幂等单位 |
| 指纹 / fingerprint | 漏洞去重标识，规则 + 文件 + 代码片段计算得出 |
| API Key | 扫描工具调用平台接口的凭证（长期有效，可吊销） |
| JWT | 平台前端用户登录后使用的会话令牌 |

## 5. 业务流程

### 5.1 主流程（时序）

```
开发者 push 代码
      │
      ▼
┌─────────────┐   拉取/安装   ┌──────────────┐
│ GitHub/GitLab│ ───────────▶ │  扫描工具(CI) │
└─────────────┘               └──────┬───────┘
                                     │ 1. POST /api/v1/ingest/scans          创建扫描批次
                                     │ 2. POST /api/v1/ingest/scans/{no}/vulnerabilities  上报漏洞
                                     │ 3. POST /api/v1/ingest/scans/{no}/samples          上报正负样本
                                     │ 4. POST /api/v1/ingest/scans/{no}/complete         结束批次
                                     ▼
                            ┌──────────────────┐
                            │  平台后端 (Node)  │  校验 API Key → 参数校验 → 去重 → 入库
                            └────────┬─────────┘
                                     ▼
                            ┌──────────────────┐
                            │   MySQL 8.0      │  projects / scan_tasks / vulnerabilities / samples
                            └────────┬─────────┘
                                     ▼
                            ┌──────────────────┐
                            │  React + AntD 前端│  登录 → 看板 → 漏洞列表/详情 → 处置
                            └──────────────────┘
```

### 5.2 关键设计决策

1. **契约先行（API-First）**：先冻结 `openapi.yaml`，扫描侧按契约写上报代码，平台侧按契约写后端 + 用 Mock 数据写前端，双方并行不阻塞。
2. **上报用 API Key，不用 JWT**：扫描工具是机器调用，使用 `X-API-Key` 请求头，长期有效、可吊销、可限定仓库范围。
3. **幂等设计**：`scanNo`（扫描批次号）是唯一键。重复上报同一批次不会产生脏数据，返回 `duplicated: true`。
4. **漏洞去重**：`fingerprint = sha256(projectId | ruleId | filePath | snippetHash)`。已存在则更新"最后发现时间 / 最新批次"，**保留人工处置过的状态**（避免每次 push 都把已修复的漏洞刷回 open）。
5. **大报文处理**：单次上报可能上万条样本，因此提供**分片上报**接口（每批默认 ≤ 500 条 / ≤ 5MB，支持 gzip）。
6. **样本与漏洞分离存储**：`samples` 表与 `vulnerabilities` 表通过 `vuln_id` 弱关联。负样本无关联漏洞。样本量大，单独索引、单独列表查询。

## 6. 角色与权限

| 角色 | 说明 | 权限 |
|---|---|---|
| `admin` | 平台管理员 | 全部权限：用户管理、API Key 管理、所有漏洞的查看与处置 |
| `auditor` | 安全审计员（默认角色） | 查看全部数据、修改漏洞状态、导出报表；不能管用户和 Key |
| `viewer` | 只读 | 只能查看与导出 |
| 扫描工具（机器） | 持 API Key | 仅上报接口（`ingest:*`），不能查询业务数据 |

权限矩阵：

| 功能 | admin | auditor | viewer | API Key |
|---|:--:|:--:|:--:|:--:|
| 上报扫描结果 | ✅ | ✅ | ✅ | ✅ |
| 查看漏洞列表/详情 | ✅ | ✅ | ✅ | ❌ |
| 修改漏洞状态/指派 | ✅ | ✅ | ❌ | ❌ |
| 导出报表 | ✅ | ✅ | ✅ | ❌ |
| 查看样本库 | ✅ | ✅ | ✅ | ❌ |
| 用户管理 | ✅ | ❌ | ❌ | ❌ |
| API Key 管理 | ✅ | ❌ | ❌ | ❌ |

## 8. 技术选型

需求方指定：**Node.js + React + Ant Design + MySQL**。以下为在此约束下的具体落地建议。

### 8.1 后端

| 项 | 选型 | 理由 |
|---|---|---|
| 运行时 | Node.js 20 LTS | 需求指定 |
| 语言 | TypeScript 5.x | 契约字段多，类型能显著降低联调成本 |
| Web 框架 | Express 4（或 NestJS，二选一） | 平台功能不复杂，Express 更轻；若团队熟 NestJS 可换 |
| ORM | Prisma 5 | 迁移与类型生成体验好；也可换 Sequelize/TypeORM |
| 数据库 | MySQL 8.0（utf8mb4） | 需求指定 |
| 校验 | zod | 上报报文做严格 schema 校验，错误信息直接返回给扫描侧 |
| 鉴权 | jsonwebtoken + bcrypt | JWT 给前端，bcrypt 存密码 |
| 日志 | pino | 结构化 JSON 日志，便于排查上报失败 |
| 接口文档 | OpenAPI 3.0 + swagger-ui-express | 自动生成可交互文档 |
| 测试 | Jest + supertest | 上报接口必须有集成测试 |

> 备用简化方案：若想更快出活，可把 Express + Prisma 换成 Express + mysql2 手写 SQL，去掉 Prisma 学习成本。**但上报接口的 zod 校验不建议省。**

### 8.2 前端

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | React 18 | 需求指定 |
| 构建 | Vite 5 | 启动快 |
| 语言 | TypeScript | 与后端共享类型 |
| 组件库 | Ant Design 5 | 需求指定："用 AntD 做起来大气，阿里的" |
| 高级组件 | @ant-design/pro-components | **强烈建议**：ProTable 直接满足"筛选 + 表格 + 分页"，ProLayout 出后台框架，省 50% 页面工作量 |
| 图表 | @ant-design/charts（或 ECharts） | 看板趋势/饼图 |
| 请求 | axios（统一封装拦截器） | 统一处理 token、错误码 |
| 路由 | react-router-dom 6 | |
| 状态 | zustand（轻量）或 React Context | 只存用户信息与全局配置，别上 Redux |
| 代码高亮 | react-syntax-highlighter | 漏洞代码片段展示 |
| 时间 | dayjs | AntD 5 已内置依赖 |

### 8.3 工程与部署

## 10. 数据库设计

库名：`vuln_platform`，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。

### 10.1 ER 关系

```
users 1───n api_keys
users 1───n vulnerabilities (assignee)
projects 1───n scan_tasks 1───n vulnerabilities 1───n vuln_events
                          └───n samples
vulnerabilities 1───0..1 samples (正样本)
```

### 10.2 DDL

```sql
SET NAMES utf8mb4;
CREATE DATABASE IF NOT EXISTS vuln_platform
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE vuln_platform;

-- ---------- 用户 ----------
CREATE TABLE users (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  username      VARCHAR(64)     NOT NULL COMMENT '登录名',
  password_hash VARCHAR(100)    NOT NULL COMMENT 'bcrypt hash',
  display_name  VARCHAR(64)     DEFAULT NULL,
  email         VARCHAR(128)    DEFAULT NULL,
  role          ENUM('admin','auditor','viewer') NOT NULL DEFAULT 'auditor',
  status        TINYINT         NOT NULL DEFAULT 1 COMMENT '1启用 0禁用',
  last_login_at DATETIME        DEFAULT NULL,
  created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_username (username)
) ENGINE=InnoDB COMMENT='平台用户';

-- ---------- API Key（扫描工具凭证） ----------
CREATE TABLE api_keys (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name          VARCHAR(64)     NOT NULL COMMENT '用途备注，如: github-actions-prod',
  key_prefix    VARCHAR(16)     NOT NULL COMMENT '明文前8位，便于识别',
  key_hash      CHAR(64)        NOT NULL COMMENT 'sha256(明文key)',
  scopes        VARCHAR(255)    NOT NULL DEFAULT 'ingest' COMMENT '权限范围，逗号分隔',
  repo_scope    VARCHAR(512)    DEFAULT NULL COMMENT '允许上报的仓库白名单，空=全部',
  expires_at    DATETIME        DEFAULT NULL COMMENT 'NULL=永不过期',
  last_used_at  DATETIME        DEFAULT NULL,
  status        TINYINT         NOT NULL DEFAULT 1 COMMENT '1启用 0吊销',
  created_by    BIGINT UNSIGNED DEFAULT NULL,
  created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_prefix (key_prefix),
  KEY idx_status (status)
) ENGINE=InnoDB COMMENT='扫描工具API凭证';

-- ---------- 项目 / 代码仓库 ----------
CREATE TABLE projects (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name           VARCHAR(128)    NOT NULL COMMENT '项目名',
  repo_type      ENUM('github','gitlab','gitee','bitbucket','other') NOT NULL DEFAULT 'other',
  repo_url       VARCHAR(512)    NOT NULL,
  repo_full_name VARCHAR(255)    DEFAULT NULL COMMENT 'org/repo',
  default_branch VARCHAR(128)    DEFAULT NULL,
  owner          VARCHAR(64)     DEFAULT NULL COMMENT '负责人',
  description    VARCHAR(512)    DEFAULT NULL,
  status         TINYINT         NOT NULL DEFAULT 1,
  created_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_repo (repo_type, repo_url(255)),
  KEY idx_name (name)
) ENGINE=InnoDB COMMENT='被扫描的项目/仓库';

-- ---------- 扫描批次 ----------
CREATE TABLE scan_tasks (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  scan_no         VARCHAR(64)     NOT NULL COMMENT '扫描侧批次号，幂等键',
  project_id      BIGINT UNSIGNED NOT NULL,
  scanner_name    VARCHAR(64)     DEFAULT NULL,
  scanner_version VARCHAR(32)     DEFAULT NULL,
  trigger_type    ENUM('push','merge_request','manual','schedule','webhook') NOT NULL DEFAULT 'push',
  branch          VARCHAR(128)    DEFAULT NULL,
  commit_id       VARCHAR(64)     DEFAULT NULL,
  commit_message  VARCHAR(512)    DEFAULT NULL,
  commit_author   VARCHAR(64)     DEFAULT NULL,
  commit_time     DATETIME        DEFAULT NULL,
  started_at      DATETIME        DEFAULT NULL,
  finished_at     DATETIME        DEFAULT NULL,
  status          ENUM('running','success','failed','partial') NOT NULL DEFAULT 'running',
  total_files     INT             NOT NULL DEFAULT 0,
  scanned_files   INT             NOT NULL DEFAULT 0,
  vuln_count      INT             NOT NULL DEFAULT 0 COMMENT '本批次去重后新增/命中漏洞数',
  sample_count    INT             NOT NULL DEFAULT 0,
  raw_report      MEDIUMTEXT      DEFAULT NULL COMMENT '原始报文(可选保留，便于追溯)',
  created_at      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_scan_no (scan_no),
  KEY idx_project_time (project_id, created_at),
  KEY idx_status (status)
) ENGINE=InnoDB COMMENT='扫描批次';

-- ---------- 漏洞 ----------
CREATE TABLE vulnerabilities (
  id               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  vuln_no          VARCHAR(32)     NOT NULL COMMENT '平台编号 VUL-20250101-0001',
  fingerprint      CHAR(64)        NOT NULL COMMENT '去重指纹',
  scan_id          BIGINT UNSIGNED NOT NULL COMMENT '最近一次命中的批次',
  project_id       BIGINT UNSIGNED NOT NULL,
  external_vuln_id VARCHAR(64)     DEFAULT NULL COMMENT '扫描工具内的漏洞ID',
  rule_id          VARCHAR(128)    DEFAULT NULL,
  rule_name        VARCHAR(255)    DEFAULT NULL,
```

## 12. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 漏洞列表接口 P95 < 300ms（10 万条数据量下）；看板接口 < 500ms |
| 容量 | 支撑 100 个项目、10 万漏洞、500 万样本；样本表历史数据可按月归档 |
| 并发 | 上报接口支持 50 QPS；平台侧限流 200 QPS |
| 可用性 | 上报接口**必须幂等**，扫描侧网络失败可安全重试 3 次 |
| 报文限制 | 单请求 ≤ 5MB（gzip 前）；单批漏洞/样本 ≤ 500 条；代码片段单条 ≤ 64KB |
| 安全 | 密码 bcrypt；API Key 只存 hash；JWT 有效期 8h；Helmet + CORS 白名单；参数化查询防注入；上报接口限流 |
| 日志 | 每次上报记录 scanNo / 上报方 IP / 条数 / 耗时 / 结果 |
| 备份 | MySQL 每日全量备份，保留 30 天 |
| 时区 | 数据库与接口统一使用 UTC 存储，前端展示按浏览器时区（UTC+8）转换 |

## 14. 开发计划

> 核心原则：**先冻结契约，再并行开发**。

| 里程碑 | 内容 | 产出 | 依赖 |
|---|---|---|---|
| M0 契约冻结（本周内） | 评审本文档与 `02-API接口文档.md`，双方确认字段、枚举、错误码 | 双方签字确认的 API 文档 + `openapi.yaml` | 扫描侧确认能提供哪些字段 |
| M1 骨架 + Mock | 搭 monorepo；用 `openapi.yaml` 起 Mock Server（prism/json-server） | 可访问的 Mock API；扫描侧可开始联调上报代码 | M0 |
| M2 后端上报链路 | 建库建表；实现 ingest 全部接口 + API Key 鉴权 + 幂等去重；集成测试 | 扫描工具能真实入库 | M1 |
| M3 后端查询与统计 | 漏洞/项目/扫描/样本查询接口 + 统计接口 + 鉴权 | 全部 P0 接口可用 | M2 |
| M4 前端 | 登录 → 布局 → 看板 → 漏洞列表/详情 → 其余页面 | 可演示的前端 | M1（用 Mock 并行） |
| M5 联调与验收 | 真实扫描工具跑通端到端；修 bug；补文档与部署脚本 | 可部署版本 | M2/M3/M4 |
| M6 增强（P1/P2） | 导出报表、Webhook、告警、审计日志 | 迭代版本 | M5 |

**并行策略**：M0 完成后，扫描侧按契约写上报、平台后端写 ingest、前端用 Mock 写页面，三条线互不阻塞。

## 15. 验收标准

1. 扫描工具在 GitHub Actions 中一次运行，能完整上报 1 个仓库的漏洞与正负样本，平台数据库可查到对应记录。
2. 同一 `scanNo` 重复上报 3 次，`vulnerabilities` 与 `samples` 表记录数**不增加**（幂等）。
3. 同一漏洞在多次 push 后重复出现，漏洞表只保留一条，`last_found_at` 更新，人工设置的 `fixed` 状态**不被覆盖**。
4. 管理员登录后能在看板看到与数据库一致的统计数字。
5. 漏洞列表支持至少 6 个条件组合筛选 + 分页，翻页与筛选结果正确。
6. 漏洞详情页代码片段正确高亮并显示行号。
7. API Key 吊销后，扫描工具再次上报返回 `40101`。
8. `docker-compose up` 后，前端与后端可正常访问，无需额外手工配置。

## 16. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 字段契约反复变更 | 双方返工 | M0 冻结；变更走版本号（`/api/v1` → `/api/v2`）或**只增字段不删改** |
| 扫描侧字段能力不足（如拿不到行号/片段） | 数据质量差 | 所有非关键字段设为可选，缺省时平台侧填 `null` 并标记 `partial` |
| 样本量爆炸导致库膨胀 | 查询变慢 | snippet 截断 + 按月归档 + 只对需要的项目保留样本 |
| 扫描工具网络抖动导致上报失败 | 数据丢失 | 幂等 + 分片 + 扫描侧本地缓存重试 |
| 前端页面多、工期紧 | 延期 | 用 ProComponents 少写代码；P1/P2 页面后置 |
